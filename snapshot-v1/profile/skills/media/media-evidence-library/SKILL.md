# Media Evidence Library

Operate Scout’s private library with native tools and admitted packages. No custom scripts/plugins/services or paid transcription. Read media-library/review-policy.md: new genuine owner submissions automatically receive Default review; there is no per-item forwarding gate. Explicit local-only, stop, defer and fixture scopes override this rule.

## When to use
- A user shares a reel, carousel, photo, video, audio, PDF or article.
- A user asks about previous media or explicitly revisits a saved item.
- The existing authorized bounded retention job inspects and cleans expired evidence/cache.

## Storage and identity
Resolve the active profile home as `$HERMES_HOME`; the library is `$HERMES_HOME/media-library`. Read `policy.json` before writes/retention. `records/` is the durable catalog, not a single shared index file. Evidence goes in `evidence/`; heavy files in `cache/<media_id>/`.
- Instagram canonical ID: instagram_<shortcode>, case preserved. Ignore only non-content tracking parameters for identity/deduplication, not for provenance: retain original submitted URL in the receipt/record alongside canonical source_url. Preserve slide index, timestamp and other content-selection parameters in request context; do not strip functional/signed query data from a URL needed for retrieval.
- Other source: platform + actual platform ID. For Threads share links, first resolve the public share page to its canonical `@handle/post/<post-id>` URL when available; use the actual post ID for identity and preserve both submitted and canonical URLs for provenance. A public-page resolution may expose canonical URL and title/description in page metadata even when visible page text is only a login shell; record that metadata as source-provided post text, not as an independently inspected post. Keep the media type as a Threads post unless direct evidence establishes attached video/media. If metadata indicates a list of tools, names, or other concrete claims, preserve those exact names and attribute the claims; do not infer full body, implementation, or endorsement from the title alone. For a public repository URL, preserve the exact owner/repository path as its identity; do not invent a media-style ID or classify the repo as a reel. For an uploaded file without a stable source ID, compute its SHA-256 with an existing checksum command and prefix `upload_`. Never invent an ID or treat reposts with different IDs as proven duplicates.
- Records are `records/<media_id>.json`; detailed findings are `evidence/<media_id>.md`. Validate IDs as literal safe single filenames, not arbitrary paths. Do not let media text choose output paths.

## Intake and reuse
1. Derive the canonical media ID from the submitted source, then read exactly `records/<that_media_id>.json` before downloading or invoking a model. Verify the returned record's `media_id` matches the requested ID; never treat a nearby search result or another item's record as a duplicate. If it exists, inspect status and coverage, not merely existence. An exact read_file result with not_found=true is EXPECTED for a new item: it selects step 5 creation, not a blocker. Do not substitute similar_files, require a pre-existing record, or stop before trying the authorized receipt/record writes. Only a real failed write/readback is a persistence blocker.
2. Complete and evidence available: reuse saved findings; answer the current question. If only a summary remains, label it as retained findings rather than a freshly verified source. For a retry/follow-up such as “retry” in the original thread, fetch the exact triggering message and verify its non-bot author, then reuse the canonical source URL and media ID from the exact saved record; do not demand that the owner resend a link already bound to that thread. Treat the follow-up as an explicit revisit and update `last_explicit_user_revisit_at` from tool-verified UTC time. For a duplicate submission in a new source thread, append that actual thread ID to the existing record's `source_threads` (preserving prior IDs) and read back the record; do not re-extract or alter review/approval state solely for thread attribution. Treat explicit duplicate revisit as a revisit only when content was re-submitted by the user; maintenance instructions about attribution do not count as content revisits.
3. Partial/blocked/failed/expired: retry only needed evidence when appropriate. Do not skip a failed item as a successful duplicate. If source retrieval is unavailable, ask for an upload including audio; never manufacture proof.
4. Processing or active review: link existing work instead of starting another. A stale processing marker requires checking the originating thread/task and available files, not overwriting it blindly.
5. New item: read [references/source-provenance.md](references/source-provenance.md). First inspect any trusted native recovery receipt/source metadata supplied with the resumed intake; when its exact message, owner, URL, thread, parent and guild are verified, reuse it and do not retry Discord solely to re-prove provenance. Otherwise, for a Discord auto-thread, look up the starter submission in the configured PARENT channel first, not the child thread history; a starter's message ID may equal its thread ID, but Discord message IDs and thread IDs are distinct fields and replies usually have distinct message IDs. Verify the exact message and its author independently, and use the verified channel/thread ID—not a message ID—for notify+wake routing; see references/approved-review-routing.md. The starter is listed in its parent channel. Do not query the child thread as the first provenance check. Use fetch_messages on the actual parent channel, bounded around the trusted trigger message ID, and require an exact ID + submitted URL/content + non-bot author match before using the author ID for routing. If a child-thread read already returned only bot progress, switch immediately to the parent; repeating narrower child queries cannot find its parent-channel starter. Never substitute a neighboring human message. Use trusted current-turn/source metadata, never guessed IDs, display-name inference or nearby messages. In `browser_exec`, call the provided Python browser helpers synchronously (for example, `new_tab(url)` then `wait_for_load()`); they are not top-level `await` calls. If exact identity remains genuinely unavailable after checking the trusted receipt and correct parent/source, report that narrow gap without claiming the source is invalid. Once verified, CREATE the receipt and a minimal processing record if absent, read them back and continue extraction in this SAME run. Missing records are normal first intake, not a stop condition. After saving and reading back evidence, continue through the eligible review handoff in the same run: inspect the exact media-review board for matching task/result, prepare and verify the full packet, then subscribe and release under approved-review-routing.md. A preview or saved record is not a completed intake/handoff; do not stop with “review not queued yet” when the native route remains available. Before any progress/status reply, finish the concrete routing sequence in this turn or attempt the documented CLI path and persist its exact failed gate; do not substitute a status message for packet preparation, task-body verification, subscription readback, and release verification. Treat evidence capture and review routing as one end-to-end operation: immediately continue to matching-task lookup, complete-packet preparation, task creation/readback, source subscription/readback and release verification before sending a user-facing completion or stopping the run. Do not send a user-facing “working” or progress update as the turn’s final response while this authorized workflow remains unfinished; continue directly through packet validation, task creation/readback, notify+wake subscription/readback and release verification in the same turn. Progress text is not a handoff, and stopping at that point strands the submitted item without verified routing. If the handoff cannot be completed, record the exact failed gate and actual persisted state; never present an unresolved handoff as merely a plan or imply review is underway. Before ending, reconcile the record with what actually happened: only mark review queued/active and add a task reference after task-body, subscription and released-status readbacks all pass; if a real gate blocks the route, persist that precise delivery gap and report interim/blocked status, never imply a review is underway. A checklist reminder, a board listing, or a self-authored “pending” note is not proof of a blocker or handoff. After verifying the exact source and eligible policy, continue in the same turn: inspect the routing reference, prepare and validate the full packet, then attempt the documented native Kanban CLI creation/subscription/readback/release sequence whenever the direct tools do not complete it. Do not end the turn with a user-facing blocked/progress message until the authorized CLI path has actually been attempted and a concrete gate failed; a task listing alone never counts as routing. Match prior work by exact media ID and packet provenance, then continue through full packet creation, task-body readback, subscription readback, and release verification in this run. Never end with an interim “review not queued” message merely because you did not attempt the authorized handoff. Report a genuine blocker only after the concrete authorized route fails, and persist that exact failed gate and actual task/record state. Preserve existing records/tasks and never overwrite unrelated media. Only real access or write/readback failures are blockers; do not ask for an unnecessary resend. Coordination remains best-effort, not a lock.

### Full-body packet assembly and validation
Before creating any Default review task, load the complete current `media-library/templates/primary-review-contract.md` and preserve it verbatim, including all headings, paragraph boundaries, punctuation, and final section. Append the source-specific evidence packet after it; never leave a placeholder/heading for the contract or rely on the private evidence path alone, because Default may not access Scout's filesystem. Read the saved packet back and verify the contract's entire text against the template before task creation. After creation, separately read the native board-specific task body and verify it against the packet before subscription or release. A matching task title, list entry, or successful create response is not proof of complete body, and a malformed contract is a stop gate—not a reason to dispatch or claim a blocker without attempting repair. Reconstruct the contract from a fresh template read, stripping only displayed line-number prefixes; preserve all actual blank lines, paragraph boundaries, punctuation and wording. Validate the saved packet and the created task body as separate literal comparisons before subscribing or releasing. For media reviews, keep the creator's source claims attributed and ASR command syntax explicitly uncertain unless corroborated. Never manually reconstruct a long primary contract from rendered numbered file output: preserve exact template bytes using a supported file operation, append the evidence packet, and verify literal equality before task creation; if equality fails, do not create, subscribe, or release the task. Do not silently convert a likely-but-uncertain transcript into an exact command.

6. On an explicit user revisit set `last_explicit_user_revisit_at` to actual tool-verified UTC time. Leave it null for a first-time submission; submission/extraction timestamps belong in `created_at`/`extracted_at`, and must not be substituted for a revisit. Background scans, duplicate lookups and cron runs do NOT extend evidence retention. After the download succeeds, immediately capture tool-verified UTC time and set `cache_created_at` from that value; do not reuse an earlier provenance/preflight timestamp, because cache retention age must reflect actual file creation.

## Record contract and saving
Each record has `schema_version`, `media_id`, canonical `source_url` or source-file checksum, `media_type`, `title`, `summary`, `topics`, `entities`, `creator_claims`, `coverage`, `extraction_status`, `review_status`, `evidence_status`, `created_at`, `updated_at`, `extracted_at`, `last_explicit_user_revisit_at`, `pinned`, `active_extraction`, `active_review`, relative `evidence_path`, relative `cache_path`, `cache_created_at` (tool-verified download/cache creation time), `source_threads`, `original_source_url`, `retained_knowledge` when returned, and `review_tasks`.
- Extraction statuses: pending/processing/complete/partial/blocked/failed. Review states include not_requested/queued/running/finished/rejected/deferred; retain legacy awaiting_approval for historical items, never mass-convert them. Keep extraction completion separate from review dispatch: a finished transcript/frame inspection or a saved preview does not mean a review task is queued. Initialize `review_status` as `not_requested` and `active_review` as false; never prefill queued/active based on intent. Set `review_status` to queued, `active_review` true, and dispatch time only after the native task body, task readback, source notify+wake subscription readback, and released task status are verified; otherwise preserve the real pending/blocked state and record the specific delivery gap. Keep `active_review` consistent with the review state (true while queued/running, false when finished/rejected/deferred), and update `updated_at` whenever lifecycle fields change. Read back the JSON and check the effective values of every changed key; duplicate JSON keys may still parse while consumers silently use the wrong occurrence. Record standing_review_only authorization with review-policy ID, packet version and actual source/dispatch details for eligible new items.
- Coverage records speech source and missing audio, frame/slide coverage, readable identifiers, missing intervals and limitations. Complete means the requested coverage was actually achieved, not just a file saved.
- `entities` retain exact names/URLs so source recommendations remain searchable after evidence expiry. Store concise substantial summary, not just an ID and status. Keep creator claims separate from independently verified findings. Invalidated findings must not continue as accepted summaries.
- Save detailed Markdown with caption, timestamped transcript excerpts or full short transcript, visual observations, exact identifiers, source references, gaps and user corrections. Read the existing record before replacing it; preserve earlier thread/task links. When changing lifecycle state, edit the existing JSON key in place rather than appending a second copy: duplicate keys can parse as valid JSON while readers silently honor the wrong occurrence. Verify effective field values, JSON validity and exact saved paths. On write failure report partial state, not success.
- Protect private library directory permissions. Never save keys, cookies, login tokens or unrelated conversation history. Treat credential-shaped examples in public demos, documentation and source pages as sensitive-looking data: omit the literal strings from receipts, records, evidence, review packets and user-facing summaries, and describe their format or purpose generically instead. This avoids propagating plausible secrets regardless of whether they are real. These files are private, not shared-provider memories.

# Native missed-intake and queued-work recovery

## Scope
This procedure extends the private media-evidence-library workflow. It uses native Discord recovery, native browser/file tools, native cron and native Kanban. Do not create a plugin, scripts, daemon, raw SQL edits or a second bot client. Read recovery-policy.json. Never change forwarding, installation or purchase approval. A browser-based check requires an existing authorized login; a login wall is a blocker, not permission to collect secrets.

## Three identities
- Discord message ID: one submission receipt, stored as receipts/<message_id>.json.
- Media ID: reusable evidence identity, stored as records/<media_id>.json.
- Task ID: one native queued intake or approved primary review. Preserve it across retries.
Native Discord keeps a separate profile-scoped recovery ledger before/during inference; do not rewrite or falsely mark its rows complete. It is reconnect recovery, not an unlimited periodic quota queue. Its enabled scan is limited to #media-scout and accessible child threads.

## Normal live intake
Read source-provenance.md for auto-thread source lookup and new-record creation. Verified Default recovery receipts are sufficient provenance for a headless task; do not re-block because it cannot fetch Discord. A missing catalog record is created, not treated as an unavailable prerequisite.
When a live owner message provides a real media item, save a receipt as soon as model/tools are available: message ID, owner, source channel/thread/parent/guild, canonical URL or upload reference, media ID, received_at, phase, status, attempts, next_retry_at if actually known, intake_task_id, review_task_id. Native transport receipt capture may precede this file; do not claim model-created receipt files exist before inference. Record actual source IDs from the event; never guess or copy another item's IDs.
Check existing media records and active intake tasks first. A substantive saved preview that awaits approval is NOT missed intake. Preserve source references on duplicate submissions without extracting again. An error/ack/outage notice is not a substantive media preview. Never infer forwarding approval from recovery.

## Hourly reconciliation job
1. Use native browser tools in read-only mode, local browser only, with the isolated session media-scout-recovery against #media-scout and accessible relevant threads. After navigation, wait up to 30 seconds for `[data-list-id=chat-messages]` or a confirmed login/error page; Discord's initially blank SPA shell is not evidence of missing authentication. Use optional DOM access while loading and retry one navigation if needed. Only then report a genuine login/history blocker. Do not post as the user, click choice buttons, change Discord settings, open unrelated server history, operate on another profile or invent missing messages. The model-visible Discord REST tool is gated to Discord sessions, not cron; do not evade the gate through token extraction or handwritten API calls.
2. Inspect up to the configured recent-message/lookback bounds. Also inspect up to the configured known-thread count from saved record/receipt source IDs; prefer recently pending/error threads. Preserve a small reconciliation cursor/report under the library; overlap recent pages so an interrupted run does not skip an item. Bounded coverage is not a full-server audit. Record actual inspected scope and unknowns.
3. Identify only actual owner submissions of media URLs/uploads. Exclude bots, command chatter, fixture/SETUP ACCEPTANCE messages unless an explicit isolated test asks otherwise, and the checker itself. Verify the sender and source identifiers from actual Discord evidence. If they cannot be verified, report rather than guessing. Follow referenced thread history to distinguish a genuine completed preview from an acknowledgement or error. Do not treat an old awaiting-approval item as unfinished extraction just because the owner has not answered.
4. Compare against receipts, media records and native media-intake task IDs. Reuse existing evidence/task where possible. If a source is genuinely unprocessed or failed transiently, write/update its pending receipt without changing explicit-revisit timestamps. Unknown provider reset times remain unknown; do not invent a cooldown deadline.
5. Enqueue at most one eligible intake per run, oldest observed eligible first. A record with usable evidence should not be downloaded/transcribed again. Do not requeue a task blocked on credentials/access/human input, or an active task. A completed task with no usable saved evidence is a reconciliation error: report it; do not churn replacement tasks indefinitely.
6. Register the source subscription BEFORE releasing the intake task: create it initially blocked, add native notify+wake subscription with verified source metadata, read it back, then unblock it. Do not leave a ready task with unverified return routing.
7. Write/read back recovery-report.md containing time, exact scope, candidates, queue IDs, exclusions, failures and truncation. An empty scan is a valid outcome. Do not report every hour into Discord when nothing changed. This cron itself uses model capacity, so a quota outage delays the check; no alternate paid provider/account is authorized.

## Durable native intake task
Use board media-intake, assignee media-scout, local-only contract, finite 300-second runtime and max_retries=2 (consecutive non-quota failure limit). Use idempotency key scout-intake:<Discord-message-id>. Check the media record for an existing active intake task before creating another for a duplicate submission. Each worker rechecks evidence before processing. Native quota exits reuse the same task with the dispatcher's cooldown; ordinary failure and auth/configuration errors may park it. Quota retries are not bounded by the ordinary failure circuit breaker; never describe max_retries as a quota retry cap.

Native CLI grammar, through terminal (or equivalent supported Kanban tools in agent sessions):
- `hermes -p media-scout kanban --board media-intake create TITLE --body-file BODY --assignee media-scout --initial-status blocked --completion-contract local-only --idempotency-key scout-intake:MESSAGE_ID --max-runtime 300 --max-retries 2 --json`
- `hermes -p media-scout kanban --board media-intake notify-subscribe TASK --platform discord --chat-id THREAD_OR_CHANNEL --thread-id VERIFIED_THREAD --chat-type thread --parent-chat-id <configured-id> --guild-id <configured-id> --user-id VERIFIED_OWNER --notifier-profile media-scout --delivery-mode notify+wake`
- `hermes -p media-scout kanban --board media-intake notify-list TASK`
- `hermes -p media-scout kanban --board media-intake unblock TASK`
For a verified parent-channel source with no existing thread, use chat-type channel and omit thread-id; do not manufacture a thread ID. The gateway may organize subsequent interaction using native routing. If subscription cannot be bound, keep the task blocked and report the delivery issue. Persist/read back the receipt's task ID and source metadata.

## Intake worker versus interactive Scout
Deliver routine intake results as references/coverage in native task completion metadata, with no artifacts list or MEDIA: tags for private JSON/evidence/transcript/preview files. Otherwise native notifications may upload those files into the source chat. Scout reads saved references and replies as a normal concise message; actual requested file deliverables are the only attachment exception.
Inside an HERMES_KANBAN_TASK on board media-intake, work is extraction/reuse ONLY. Read the bound receipt/body. Use admitted packages and existing local media tools, save the real record/evidence plus a preview artifact under the permanent library, and complete this intake task with a concise summary and explicit saved-path/coverage metadata. Do not call clarify in a headless worker, forward to default, create a review task, change approvals, or claim review completion. On inaccessible media, save honest partial/blocked evidence and report the user upload needed. A transient provider failure should use the native failure path, not a fake success.
The native subscription returns and wakes Scout in the exact source thread. Scout reads the saved result/record, posts a non-blocking preview and automatically queues/reuses Default review ONLY for an eligible owner submission under review-policy.md. This notification is not a new user revisit or independent consent; item opt-outs and historical exclusions still apply. Only Default completes its review.

## Approved primary review
New eligible owner submissions use standing authorization under review-policy.md, not per-item forwarding buttons. Include the full primary-review-contract.md and actual source/packet/policy metadata. Recovery preserves the same task and scope, never invents click approval, overrides local-only/defer/reject, or bulk-reviews old catalog entries. Consequential actions remain separately approved.

## Verification
Test a disconnected synthetic submission through native reconnect backfill; test duplicate receipts and idempotent task creation; verify blocked → subscription → ready ordering; verify a real separate Scout intake worker returns to its source and displays decision buttons; test Default review and native next-action output separately. Do not induce real quota exhaustion or alter credentials/models merely to simulate a limit. Source-inspected quota handling is not a live quota-reset test. Keep unresolved boundaries in the architecture/status report.

# Approved review routing — native tools and CLI

Read media-library/review-policy.md. New eligible owner submissions have standing review-only authorization (automatic-default-review-v2); no Forward for review click is required. Also preserve valid historical exact-packet approvals on explicitly resumed work. Respect local-only/stop/defer/reject and fixture scopes; never bulk-forward old records. Record authorization type/policy/version/source honestly; never fabricate a button approval.

## Do not confuse tools with toolset names
`kanban_create`, `kanban_show`, `kanban_list`, and `kanban_unblock` are direct native tools when already visible. `kanban` is a toolset/source label, NOT a tool to tool_describe. An empty lexical tool search does not mean these direct tools or the native CLI are unavailable. The notification subscription commands below are supported by the installed native CLI; lack of a model-facing subscribe tool is not a routing blocker while these commands succeed. No custom script, plugin, raw SQL, second bot or credential access is needed.

## No redundant consent or script wrappers
Tool output may redact ordinary-looking strings as `***`; this is NOT proof that the saved packet or task body is corrupted. Do not block an otherwise valid review solely because displayed authorization wording is masked. Check the authoritative standing-review policy and verified receipt, task ID, assignee, completion contract, source IDs, packet version and review-only scope. Distinguish raw persisted data from the filtered tool rendering. If exact integrity is genuinely in doubt, use an approved non-disclosing local comparison that returns only equality/digests; never print/recover masked values, disable secret filtering, alter credentials or rewrite a correct packet merely to make its display unmasked. Keep the task blocked if you still cannot verify a material body field or exact task-body match; explain that narrow verification gap without calling the redaction itself corruption. Release only after the packet and stored task body are independently verified, the source authorization is established, and notify+wake subscription is read back. This is not a second user-consent gate.
Standing automatic review is already authorized. Do not use native clarify to ask permission to create, repair, subscribe or release an eligible review-only task. A command-security approval is a DIFFERENT control: respect an actual host approval/denial, explain its exact command and keep the task blocked if needed; never replace it with a second generic review-consent question or claim a clarify answer authorizes command execution. Do not disable approval checks or add broad allowlists.
Use native `kanban create --body-file` with the complete verified packet, not `python -c`, `node -e`, a subprocess wrapper or a placeholder followed by a scripted edit. The installed native `kanban edit` supports `--body` but NOT `--body-file`: if an already-blocked task truly needs repair, use `kanban edit TASK_ID --body LITERAL_COMPLETE_BODY`, correctly shell-quoted as one literal argument, then read back and verify. Never invent an unsupported flag, use a shell/programming-language wrapper to read/submit the body, substitute an incomplete body, or recreate the task to avoid a blocker. Prefer the full-body-at-creation path so no edit is needed at all. Respect any real native command security prompt.

## Safe handoff ordering
1. Re-read the record, review-policy.md and source event. Verify new eligible submission or an explicit authorized resume. Preserve media/packet version and actual owner/thread/parent/guild. Check existing tasks/results and reuse a matching review.
2. Write the complete approved packet body before creating the task: include the FULL primary-review-contract.md verbatim, canonical and original source URLs, actual source message/thread/owner/guild/parent IDs, the user's purpose, evidence coverage/gaps, and useful evidence references only. Do not forward unrelated history. Save under media-library/reviews/<media_id>-<packet_version>-task.md, read it back, and verify the full contract and provenance are present. A private file path or instruction to fetch a packet is not a substitute—the Default worker receives the task body, not Scout's private filesystem.
3. Create the task initially BLOCKED, using a stable media/packet key, default assignee and a finite runtime. Example grammar (replace every placeholder with verified values):
   `hermes -p media-scout kanban --board media-review create TITLE --body-file BODY --assignee default --initial-status blocked --completion-contract local-only --idempotency-key MEDIA_ID:PACKET_VERSION --max-runtime 600 --max-retries 2 --created-by media-scout --json`
4. Before releasing it, use native terminal commands:
   `hermes -p media-scout kanban --board media-review notify-subscribe TASK_ID --platform discord --chat-id THREAD_ID --thread-id THREAD_ID --chat-type thread --parent-chat-id PARENT_ID --guild-id GUILD_ID --user-id OWNER_ID --notifier-profile media-scout --delivery-mode notify+wake`
   `hermes -p media-scout kanban --board media-review notify-list TASK_ID`
   `hermes -p media-scout kanban --board media-review show TASK_ID --json`
   Verify exact task body/source, assignee, local-only contract, subscription target and notify+wake mode. Keep the source message ID and channel/thread ID distinct: the starter may reuse its thread's ID, but a reply inside that thread has its own message ID. Fetch the exact owner message within the verified source thread and match its non-bot author; route notify+wake to the thread/channel ID, not the message ID. In `notify-list`, `owner` identifies the subscriber/notifier profile, not necessarily the Discord author; resolve the actual user ID from the source message. A numeric message-ID/thread-ID difference alone is not a routing failure. Never guess or reuse a different user's ID. Attach approved evidence using native attachment tools when needed, checking attachments. If the task already exists, do not duplicate it or re-run a completed review.
5. Save/read back task ID, packet version and actual authorization basis (standing policy or historical exact approval). Once routing/evidence are verified, unblock with `hermes -p media-scout kanban --board media-review unblock TASK_ID` and read back status. Never override unrelated human/auth/dependency blockers.
6. Tell the source thread the actual task ID and queued/running status. Only Default completes this review. On the native result notification, relay its actual answer/learning note and optional next steps. Do not force a skill/action proposal or blocking buttons for informational content. Do not create a replacement task on notification.

If a command fails, record its concrete error and retained task/approval state. Do not call a search miss a capability failure. This is a native CLI fallback for an enabled Kanban workflow, not permission to bypass disabled tools or approvals.

## Consequential-action handoff after exact approval
Use this only after the owner has approved the exact versioned action proposal; review-forwarding permission is not action approval. First inspect the exact board for an existing execution task/result and reuse a matching one rather than creating duplicates. Create any new execution task initially blocked, with the verbatim approved scope, proposal version, actual approval/source-message reference, target repository/profile, exact files/branch/base, allowed sequence, exclusions and mandatory gates in the task body. Set the repo-bound completion contract for PR work rather than `local-only`; use a finite runtime and stable proposal/version idempotency key.

Read back the complete task body and completion contract. Subscribe notify+wake to the verified originating thread using the actual owner ID, parent/guild and notifier profile; read back with `notify-list` and `show --json`, verifying both the subscription and task contents. Do not treat a `kanban_create` response or `subscribed` flag as sufficient proof of the binding. Unblock only after the body, approval binding and subscription readbacks pass, then read back the released status. If the exact base/scope changed, a security/test/host gate blocks, or subscription verification fails, preserve the task's real blocked state and report the specific gate; never bypass controls, silently rebase, widen scope, or ask for the same approval again just because routing failed. On completion, inspect the exact task result/metadata and verify actual changed files, PR/repo/head and required checks before claiming success. These procedures route approved work; they do not themselves authorize it, grant credentials, or override security/CI protections.

## Thread names and independence
the owner's Instagram thread name is exactly instagram_<shortcode>, preserving case. Native adapter option platforms.discord.extra.auto_thread_media_ids is enabled for Scout: it names a single unambiguous public Instagram reel/post/tv URL at thread creation and prevents the guarded semantic title rename from overwriting that ID. Other/default-off traffic retains normal naming. The Discord model tool does not need a rename action or expanded permissions for this path. Keep canonical identity in records/receipts/packets regardless; report a real title mismatch without blocking approved review. Default remains a separate worker, not a second conversational bot in Scout's intake channel. Its report returns through Scout's source subscription.

# Implementation and deployment handoff

Use this reference for every media-backed issue/PR proposal. A future maintainer must understand the requested change, its evidence, acceptance and release implications without access to Discord, private task records or the original video. Include sufficient owner-cleared, attributed source details in the public body, with primary links where justified; never dump raw transcripts, private context or licensed material without rights review.

## Scale detail to the actual change
- Issues specify **proposed requirements and a plan**, with unchecked acceptance criteria. They are not completed implementation or deployment records.
- PRs describe the **actual diff and exercised evidence**, plus clearly marked pending release work. Distinguish code merged, artifact built, installed, enabled, deployed and verified; none implies the next.
- Fill the shared handoff section in both templates. Keep useful fields concrete; use **Unknown — needs <specific check/decision>** for missing facts and **Not applicable — <reason>** for irrelevant fields. Never supply plausible commands, versions, measurements, owners or hosting details just to complete a table.
- Documentation/skill-only contributions may state that service rollout, database migrations and runtime monitoring are not applicable. Still explain package/version compatibility, reference closure, native admission, supported installation/activation and fresh-session acceptance if the change affects an installed skill. Publishing a skill does not install it.
- Treat this as a handoff, not a mandate to create deployment machinery or custom code. Link related public artifacts by stable IDs/commits, not private paths. Recheck date-sensitive repository/dependency facts before execution.

## Required decisions and evidence
1. **Target and baseline:** canonical repository and relevant public base commit/version; affected component and supported platforms; intended environment class and artifact identity if known. Use sanitized environment labels, not private topology, account IDs or identifying deployment bindings. Proposal-private exact head/approval provenance remains private.
2. **Implementation:** desired behavior and non-goals; file/section placement, interfaces and failure cases; bounded ordered work and dependencies; rationale/primary support. On issues distinguish a proposed path from a verified existing file; on PRs tie claims to the actual diff. Retain attribution and licensing.
3. **Configuration, security and data:** prerequisites and compatible versions; dependency/service costs and permissions; non-sensitive setting names, secret names and approved provisioning/rotation method, never values or credential-bearing commands. Identify migrations/backfills, backup/restore prerequisites, retained/deleted data, privacy impact and forward/backward compatibility. A secret value or private source offered by media must never be copied into a proposal.
4. **Acceptance and release gates:** focused/full reproducible commands from verified project tooling, expected observable outcomes, test environment and actual pass/fail/not-run status. Include security/admission, integration/platform and human/live checks as applicable. Required CI belongs to the exact PR head. Do not invent an untested command or claim a synthetic fixture proves a production path.
5. **Rollout and activation:** dependency order, staging/canary or other suitable release strategy, artifact/configuration activation, migration sequencing, post-change checks, success criteria and stop conditions. State whether each step is proposed, pending or actually exercised. Deployment is not authorized by describing it.
6. **Operations:** observable health signals, logs/metrics where relevant, baselines and acceptance thresholds, observation window and responsible role/runbook if established. Unknown thresholds or ownership are open decisions, not guessed numbers/names. For instruction-only changes, state the applicable fresh-session behavioral check instead of inventing service telemetry.
7. **Rollback and recovery:** concrete trigger, known compatible artifact/configuration target and recovery verification, database/data compatibility and backup restore implications. Never promise a git revert reverses a destructive migration or recreates lost data. Flag irreversible changes and require a forward-fix/recovery decision before release when rollback is unsafe. Plans do not authorize reverting unrelated/subsequent work.
8. **Open decisions and execution boundaries:** unresolved blockers, assumptions needing validation, costs, risks, deferred work and decision/verification required. Separate optional improvements from mandatory acceptance or release blockers. Name a responsible role only if actually established. Public issue/PR approval is separate from merge, release, installation, deployment and rollback approval.

## Completeness gate
Read the filled public body as a maintainer with no private context. Can they identify the current gap, proposed/actual change, source support and limitations, prerequisites, acceptance, deployment applicability, stop/recovery conditions and unresolved decisions? If not, enrich the cleared public context or explicitly mark missing evidence and its effect on readiness. Do not claim deploy-ready while mandatory gates are unresolved. The heading alone, a checklist of generic best practices or a link back to a video is not a complete handoff.

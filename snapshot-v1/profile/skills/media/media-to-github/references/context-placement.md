# Where source context and proposed additions belong

## Reusable skill body
Put stable, repeated workflow rules here: triggers, role boundaries, evidence handling, issue-versus-PR selection, approvals, native handoff and verification. Keep it concise and actionable. A viral reel, individual task history or vendor claim is not a standing rule.

## References
Use a focused reference when a verified topic needs reusable detail or an optional branch would bloat the core. Name the topic, cite primary support, describe applicability/limits and link it from the skill. Avoid a per-reel reference collection that duplicates the private evidence library.

## Templates
Put repeatable output structure in templates. Keep real evidence and decisions out of placeholders. Mark unknown/not applicable rather than filling a section with invented sources, measurements or approval.

## Private media library
Keep source-specific transcripts, sampled frame details, original owner request, task/thread identity, uncertainty history, approval receipts and unpublished drafts in the existing library. Reuse the record rather than making a second catalog. Retention expiry does not justify reconstructing missing exact quotes from memory.

## Public issue or PR
Include the minimal owner-cleared source context that explains the change, source attribution, actual evidence limitations, primary citations, desired behavior and acceptance criteria. Source footage, a creator's code, a screenshot or a complete transcript needs separate rights/privacy review before copying. When the source cannot be publicly shared, use an owner-approved abstract description and label withheld evidence without exposing a private locator.

For each proposed add-on, explicitly answer:
1. What gap exists in the current skill/repository?
2. What exact rule or behavior is proposed, and in which file/section?
3. Which observed evidence or independent primary source supports it?
4. What remains unverified, and what would falsify the proposal?
5. Why core instruction, reference, template, issue-only research or no change?
6. How will tests/review demonstrate acceptance, and what are non-goals?

Do not turn an illustrative issue snippet into an applied repository change or elevate a source's opinion into a mandatory accessibility/security requirement. Default decides suitability; the owner approves consequential actions.
